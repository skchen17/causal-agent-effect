# 5 个核心论点 + 3 个论文方向 — 潜力评估

## 核心论点评估

### 论点 1: 从静态黑名单到因果预测

**潜力: 中高 · 但需重新命名**

标称的 do-calculus（P(s' | do(a), s)）与实际实现之间存在落差。系统做的是**带时间先后的统计关联学习**——从 before/after 快照中学习转移频率，用 Laplace 平滑算置信度。没有随机化、没有后门调整、没有反事实推理。这不是真正的因果推断，而是**统计转移学习**（statistical transition learning）。

如果在因果 ML 会议上用"do-calculus"的旗号投稿，评审会直接指出这个 gap。但如果诚实定位为 "learned transition statistics" 或 "empirical effect prediction"，反而在安全/agent 领域是新颖的——因为没人做过用执行历史来自动预测效果的 agent 安全系统。

**建议**: 去掉 do-calculus 的过度宣称，聚焦"从观测中学习效果转移"这一实际贡献。这本身已经足够新。

---

### 论点 2: 决策 = f(效果, 置信度, 上下文)

**潜力: 中**

公式本身干净，但实现是一个 if-else 级联（`ConstraintChecker.check()`），不是学习出的决策函数。"上下文"目前是手动离散化的少数几个 bucket 特征——file_count 用 4 个桶、drafts/sent 用 3 个桶、几个布尔 flag + workspace hash。这个特征工程是合理的，但远不足以支撑"上下文感知"的宣称来作为学术贡献。

真正的价值在于**架构的模块化**：决策不再和工具名耦合，任何新工具只要产生已知效果类型就会被现有逻辑覆盖。这是一个真实存在的工程优势，但需要实验来证明它比静态 permission 系统产生更少的误报/漏报。

**建议**: 做对照实验——同样的工具调用序列，CAR 的拦截率 vs 静态黑名单的拦截率，看 CAR 是否能减少"该放的被拦"和"该拦的放行"。

---

### 论点 3: 自改进安全

**潜力: 高 · 这是最强的论点**

五个论点中最有学术价值的一个。"系统越用越安全"是一个可以精确量化的主张：
- 定义 safety 指标（如：高风险动作被正确拦截的比例）
- 随观测次数 N 增长追踪指标变化
- 展示 confidence 曲线收敛

但目前的实现有几个弱点需要直面：
1. **没有遗忘机制**: 如果用户总是批准危险操作，系统会学到"危险动作是安全的"
2. **状态空间爆炸**: 当前只有少量特征，如果扩展到真实 agent 的全部上下文，组合爆炸会稀释统计
3. **Laplace 平滑是最简单的平滑**: 对于序列决策问题，可能需要 Bayesian 更新或其他不那么 naïve 的方法

第一个问题尤其严重——这意味着 CAR 的安全性实际上依赖于用户的判断力，而不是系统自身。如果用户犯错，系统会学习并强化这个错误。这是自改进安全主张最容易被攻击的点。

**建议**: 这是最值得深挖的方向。需要一个实验来展示 confidence 时间序列 + 决策质量随时间的变化。同时需要在论文中诚实讨论"学习用户错误"的问题，把它作为 limitation 并在 discussion 中提出解决方案（如：hard-coded CRITICAL tier 不可被学习覆盖、引入负面反馈机制等）。

---

### 论点 4: 可审计的 AI 安全

**潜力: 中低 · 作为独立论点不足**

ProofObject 设计干净，三层对比（预测→决策→实际）确实比普通的审计日志多了一层因果含义。但审计日志本身已被充分研究，单独作为论文贡献不够。

真正的差异化在别处：**不是因为有了审计日志，而是因为审计日志中包含了可以用于事后归因的因果证据**。比如你可以问："这个 action 为什么被 block？"→ 答案不是"因为 terminal 在黑名单上"，而是"因为我们过去观察到 terminal 在当前状态下有 73% 的概率导致 command_executed，这触发了 HIGH tier 的拦截规则"。

这个能力是新的，但它只在配合论点 3（自改进）和论点 2（基于效果的决策）时才有意义——审计之所以有用是因为决策本身是可解释的。单独拿出来作为贡献偏弱。

**建议**: 不要作为独立论点，而是作为自改进安全系统的**必要组成部分**——没有审计就无法验证自改进是否真的发生了。

---

### 论点 5: 冷启动与热运行的一致性

**潜力: 低 · 作为独立论点**

从 bootstrap 保守策略平滑过渡到因果记忆驱动的决策——这是一个优雅的工程设计，但本质上是系统实现细节，不是研究贡献。任何从规则到学习的系统都需要冷启动策略。

如果在论文的 System Design 部分花半页篇幅解释这个设计选择及其动机，是合理的。但作为一个独立论点或贡献去推，评审不会买账。

**建议**: 放在论文的 Design/Architecture 部分作为工程决策阐述，不要作为贡献声明。

---

## 论文方向评估

### 方向 A: 安全/AI Safety

**潜力: 最高 · 推荐首选**

安全社区（SaTML、AIES、FAccT、乃至 ACL 的 safety track）对 RLHF 之外的安全方案有真实需求。CAR 的独特卖点：
- **不需要训练**: 不像 RLHF 需要 GPU 集群和人类标注，CAR 从在线执行中学习
- **可解释**: 每个决策都有 evidence chain，比神经网络安全分类器透明
- **自改进**: 部署后持续变好，不需要重新训练

竞争分析：当前 agent 安全的主流方案是三类——(a) 静态 permission 系统（OpenAI、LangChain），(b) RLHF 对齐（Anthropic），(c) 宪法 AI/规则引擎。CAR 不在这三类中，它创造了一个新类别：**基于执行统计的自改进安全**。这是最有利的定位。

**需要什么才能发表**:
- 一个基准数据集：N 个 agent 任务的工具调用序列，标注每个调用是否安全
- 对比实验：CAR vs 静态黑名单 vs 始终确认 vs 始终放行
- 关键指标：误报率（false positive）、漏报率（false negative）、用户负担（确认次数/总调用次数）
- 展示学习曲线：随执行次数增加，上述指标如何变化

---

### 方向 B: Agent 系统

**潜力: 中 · 适合短文/demo**

系统会议（如 EuroSys、SOSP 的 AI track、或专门的 agent workshop）重视部署经验。CAR 确实是一个真实的、在 Hermes 中运行的系统，与纯模拟不同。但系统论文需要规模——单个 agent 在一个工作区中的执行历史不够。

当前实现约 500 行 Python + SQLite 单表，没有分布式架构、没有性能评估、没有多租户隔离。作为系统论文证据不足。

**适合的形式**:
- 一个 4-6 页的 short paper / demo paper 展示架构
- 或者作为一个更大系统论文中的 safety 模块

**不建议**: 作为主要投稿目标，除非系统规模显著扩大。

---

### 方向 C: 因果推断

**潜力: 低 · 当前不建议**

如论点 1 的分析，系统在"因果"的宣称与实现之间有显著 gap。当前实现是统计关联学习（statistical association + temporal precedence），缺少因果推断的核心要素：
- 没有干预 vs 观测的区分
- 没有混杂因子控制
- 没有反事实推理
- 没有 do-calculus 的实际计算

如果在 UAI、CLeaR、NeurIPS 因果 track 投稿，评审会很快指出这些问题。**除非系统加入真正的因果推断机制**（如：随机化某些工具执行来区分相关和因果），否则不建议走这个方向。

---

## 总结：推荐策略

| 优先级 | 方向 | 核心论点 | 还需要什么 |
|--------|------|----------|-----------|
| **P0** | AI Safety | #3 自改进 + #2 效果决策 | 基准数据集 + 对照实验 + 学习曲线 |
| **P1** | Agent 系统 | 架构设计 | 系统规模扩大 或 改为短文/demo |
| **P2** | 因果推断 | — | 需大幅重做因果机制，暂不推荐 |

**最值得做的实验**: 构建一个 agent safety benchmark，用 CAR 的三个阶段（冷启动 → 100 次执行后 → 1000 次执行后）对比静态黑名单，展示：(1) 误报率下降，(2) 漏报率保持或下降，(3) 用户确认负担降低。如果这三个指标都朝正确的方向移动，论文就有了实证 backbone。

**最大的理论风险**: "自改进安全"实际上学习的是用户的判断习惯，而不是客观安全。如果用户犯错，系统会放大错误。需要在论文中正面应对这个挑战，不能回避。
